Flash-Decoding：把 KV 切块并行算，长上下文解码快 8 倍

Flash-Decoding：把 KV 切块并行算，长上下文解码快 8 倍（中文精读）

  • 原文：Flash-Decoding for long-context inference（https://crfm.stanford.edu/2023/10/12/flashdecoding.html）
  • 收藏：2026-11-24
  • 主题：并行策略（推理）/ 解码注意力
  • 一句话要点：斯坦福 CRFM 的 Flash-Decoding 给解码注意力多并行了一个维度——键值序列长度：把 KV 切成小块并行算，每块多记一个 log-sum-exp，最后一步缩放到一起；CodeLlama 34B 上端到端解码在很长序列上快 8 倍，注意力本身比 FlashAttention 快 50 倍。

为什么值得读

解码是 LLM 推理的瓶颈形态：一次生成一个 token，每步都要对全部历史 token 做注意力。FlashAttention 把训练注意力优化得很好了，但它的并行维度是 batch 与 query 长度；解码时 query 长度是 1，batch 一小就占不满 GPU，batch 为 1 时 A100 的 108 个 SM 只用上不到 1%。Flash-Decoding 的改动很小、收益很大：沿键值序列长度再并行一次，batch 再小、只要上下文够长就能把 GPU 占满。这篇是这个方法的原始出处，机制、动图、基准三部分都全，读完就能理解为什么后来 FlashAttention 2.2 与 xFormers 都默认带上它。

核心结论

  • 并行维度是关键：FlashAttention 只沿 batch 与 query 长度并行；解码时 query 长度通常是 1，batch 小于 GPU 的 SM 数（A100 是 108 个）就占不满 GPU；长上下文要塞进显存只能用更小的 batch，batch 为 1 时 FlashAttention 用的 GPU 不到 1%。
  • 三步算法：先把键值切成更小的块；每块用 FlashAttention 并行算 query 的注意力，每行每块多写一个标量（注意力值的 log-sum-exp）；最后对全部块做规约，用 log-sum-exp 缩放每块的贡献得到实际输出。切分只是完整键值张量的视图，不产生 GPU 操作；整个流程是两个 kernel，分别执行第 2 步与第 3 步。
  • 数学基础：注意力/softmax 可以迭代计算；Flash-Decoding 在两个层面用它：块内（像 FlashAttention 一样），以及跨块做最后的规约。
  • 基准（CodeLlama 34B，batch 为 1，序列 512 到 64k，4 卡并行）：端到端解码在很大的序列上快 8 倍，扩展性远好于 PyTorch 原语、FlashAttention v2（v2.2 之前）、FasterTransformer；小 prompt 时各方法相近，序列从 512 拉到 64k，只有 Flash-Decoding 基本不掉速。
  • 微基准（A100，f16，batch 为 1，16 个 query 头、每头维度 128、2 个键值头，分组 query 注意力）：注意力本身比 FlashAttention 快 50 倍；序列长度到 32k 之前注意力耗时大致恒定；拉到 64k 运行时间几乎恒定。
  • 落地：FlashAttention 包从 2.2 版起、xFormers 从 0.0.22 版起可用；xFormers 的分发器按问题规模自动选用 Flash-Decoding 或 FlashAttention，两者都不支持时分发到实现 Flash-Decoding 算法的高效 Triton kernel。

逐节要点

解码为什么贵

生成一条回复只要约 $0.01（AWS 上 8 块 A100 实例跑几秒），但放大到数十亿用户、每人每天多次交互，成本很快累积；代码补全每敲一个字符就跑一次，更贵。解码是迭代过程：一次生成一个 token，生成 N 个 token 的完整句子要过 N 次模型；以前算过的 token 可以缓存，单步生成不依赖上下文长度，只有一个操作例外——注意力。长上下文用例越来越多：推理更长文档、做摘要或回答问题、跟踪更长对话、处理整个代码库再写代码；2022 年多数 LLM 上下文只有 2k（GPT-3），现在开源 LLM 已到 32k（Llama-2-32k），甚至 100k（CodeLlama）。沿 batch 维度放大时，即使上下文相对小，注意力也会成为瓶颈：要读的内存随 batch 维度增长，而模型其余部分的内存只取决于模型大小。

解码时的多头注意力

每生成一个新 token 都要关注全部历史 token，算 softmax(QKᵀ)V。训练场景的 FlashAttention 优化的是读写中间结果的内存带宽，推理的瓶颈不同。矩阵乘法原语不用 FlashAttention 也能做注意力：操作占满整个 GPU，但启动很多 kernel、反复写读中间结果，并不理想。动图对比：FlashAttention 只沿 query 块与 batch 并行，解码时占不满整个 GPU。

更快的解码注意力：Flash-Decoding

基于 FlashAttention，多并行一个维度：键值序列长度。好处两者兼得：像 FlashAttention 一样只向全局内存写很少的额外数据；batch 很小、上下文够长时也能充分利用 GPU。动图对比：Flash-Decoding 还沿键和值并行，代价只是最后多一步小规约。

CodeLlama 34B 上的基准

对比的几种方法：PyTorch 纯原语、FlashAttention v2（v2.2 之前）、FasterTransformer 注意力 kernel、Flash-Decoding，以及一个上界（从内存读出整个模型与 KV 缓存所需的时间）。端到端解码速度（token/秒）随 prompt 长度变化：小 prompt 时各方法相近；序列从 512 拉到 64k，Flash-Decoding 在 batch 为 1 时序列长度对生成速度几乎没有影响。

组件级微基准

微基准表（运行时间，微秒）显示：Flash-Decoding 在各 batch 与序列长度组合下运行时间基本稳定在 56–107 微秒，而 PyTorch 原语在 1,335–3,223 微秒、FlashAttention v2.0.9 在 352–4,592 微秒；序列越长差距越大（batch 为 1、序列 131,072 时：2,664 / 4,592.2 / 106.6）。

用上 Flash-Decoding

LLaMA v2 / CodeLlama 的完整解码示例在 FlashAttention 仓库与 xFormers 仓库里；另有一个面向 LLaMA v1/v2 模型的高效解码最小示例，追求快、易读、有教学意义、可改。

局限

  • 方法针对解码场景：训练时 query 长度大，FlashAttention 本来的并行维度已经够用，Flash-Decoding 的额外并行没有同等收益。
  • 最后一步规约是额外成本：并行收益要大于规约开销，上下文够长时才划算；小 prompt 时各方法表现相近。
  • 微基准的恒定耗时只到 32k：超过后注意力耗时开始上升（序列 131,072 时 106.6 微秒，高于 64k 时的 64.4 微秒）。

可复用的点

  • 并行维度的选择：算子并行不够时，沿数据维度再找一个可并行的轴（这里是 KV 序列长度），而不是只调 batch。
  • log-sum-exp 规约：分块算注意力时，每块多存一个标量就能无损合并，核心是 softmax 可迭代计算。
  • 切分即视图：分块本身不产生 GPU 操作、不复制数据，成本只在两个 kernel。
  • 恒定耗时设计目标：长上下文解码里让注意力耗时不随序列长度增长，端到端速度就稳住了。
