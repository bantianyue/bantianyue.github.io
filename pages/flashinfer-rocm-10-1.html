FlashInfer 登陆 ROCm 10.1：API 不变，backend=auto 逐调用选核

FlashInfer 登陆 ROCm 10.1：API 不变，backend=auto 逐调用选核（4⭐，No.149）

一句话要点：FlashInfer 的 API 完整搬上 AMD ROCm 10.1，解码、预填充、MLA 包装保持上游 v0.6.18 的签名与参数顺序；backend="auto" 在每个调用上按逐架构路由表在 AITER 与树内 HIP 核之间选核。

为什么值得读：这是 FlashInfer 首次在 AMD 平台上提供与 CUDA 相同的调用面，且路由决策是逐调用、逐架构的，不是编译期开关；CDNA4 的一条转置指令替换 6 次洗牌、FP8 编码不对称、构建只认 Docker 钉住配置，三个细节都直接决定能不能在 MI300/MI350 上把库跑起来。

核心结论： - API 本身与 CUDA 上相同：相同的包装、相同的 plan() 与 run() 模型；解码、预填充、MLA 包装保持上游 FlashInfer v0.6.18 的签名，连参数顺序都不变。 - API 之下，树内 HIP 核与 AITER 按调用分工，backend="auto" 逐调用选：plan() 先问 AITER 能不能接这个调用（数据类型、KV 排布、掩码、头维度），再按两个架构上实测的逐架构路由规则选；规则在一张表里（flashinfer/rocm/arch_caps.py），仓库的支持矩阵就是从这张表生成的。 - AITER 在 C++ 层面集成：调用跑在 AITER 上时，FlashInfer 从自己的 C++ 代码启动核——直接加载 AITER 编译好的注意力核，或链接 AITER 的 C++ 入口（MoE、norm、激活、RoPE 与 KV append），而不是走 AITER 的 Python API；AITER 的 Python 一侧只在 plan() 时、或对没有 plan() 的算子在第一次调用时，用来构建、定位或探测核变体；MLA 是唯一仍经 Python 跑 AITER 的算子。 - AITER 的 MoE 是编译好的、按架构选的变体：按 EP（专家并行）规模、每个 token 的 top-k 个专家、以及 expert-parallel 的通信方式挑核；这三个量决定了选哪个编译好的核变体与通信路径。 - CDNA4（gfx950）上，FMA 分块与共享内存之间搬运是按 16 字节向量做的，16 字节向量是一次加载的量：FMA 的分块按行来算，每次加载对应一行。加载的向量分两半：前半部分的 8 个元素进一个寄存器，后半部分的 8 个元素进另一个寄存器。 - CDNA4 一条指令 ds_read_b64_tr_b16 做转置 V，替换 6 次 ds_bpermute_b32 跨通道洗牌：种子重算，共享内存排布不变；这是一个 CDNA4 专属的转置读取指令。 - plan() 之后，批量预填充与批量解码包装在 wrapper.backend 里报告选择（AITER 是 aiter，树内核是 fa2），大多数 AITER 拒绝的原因在 wrapper.backend_fallback_reason 里。 - FP8 编码不对称（最容易踩的坑）：树内核只认 FNUZ，OCP 会被静默读错；gfx950 上给 AITER FP8 预填充写的 KV 缓存，解码读不了。 - 构建只支持 Docker 镜像钉住的配置（ROCm 10.1.0、PyTorch 2.12.0、Python 3.12、Ubuntu 24.04、amd-aiter 0.1.21.post2）；torch.compile 在 ROCm 上没有后端支持，FlashInfer 的包装是按编译后的图里的注意力调用来做的，两个栈互不干涉。 - 上游 v0.6.18 更大，缺失的部分按原因分：ROCm 上不支持的是包 CUDA 专属库、PTX、SM 门控核或 CuTe DSL 的模块；没有 ROCm 实现的是不沾这些的普通核；layernorm 与量化 norm 算子能导入、调用时失败（ROCm 的 norm 绑定没有导出它们）。

一、新版本带来什么

FlashInfer on ROCm 把它的 API 带到 AMD Instinct GPU 上。本版接续预填充注意力版本：级联注意力、多头潜在注意力（MLA）、独立的旋转位置编码（RoPE）算子已经落地；新加 FP8 预填充、POD-Attention（预填充与解码叠在一个核里）、融合 MoE，以及图捕获下的 AITER 解码；全部跑在 CDNA3（gfx942：MI300X、MI325X）与 CDNA4（gfx950：MI350X、MI355X）上。

二、AITER 集成与逐调用路由

AITER 是 AMD 的推理核库，FlashInfer 在 ROCm 上把它当作第二后端。路由发生在每个调用上：plan() 先问 AITER 能不能接这个调用，再按逐架构路由表选核；选完后 wrapper.backend 报告选择（aiter 或 fa2），拒绝原因写在 wrapper.backend_fallback_reason 里。AITER 的 MoE 按 EP 规模、top-k 专家数、expert-parallel 通信方式挑编译好的核变体。

三、CDNA4 的转置指令与共享内存排布

CDNA4 上 FMA 分块与共享内存之间的搬运按 16 字节向量做，每次加载对应一行；向量分两半进两个寄存器。一条 ds_read_b64_tr_b16 指令做转置 V，替换 6 次 ds_bpermute_b32 跨通道洗牌，种子重算、共享内存排布不变。

四、FP8 编码不对称

树内核只认 FNUZ，OCP 会被静默读错；gfx950 上给 AITER FP8 预填充写的 KV 缓存，解码读不了。FP8 KV 缓存的读写双方必须用同一编码，否则是静默错误，不是报错。

五、构建与缺失的模块

构建只支持 Docker 镜像钉住的配置（ROCm 10.1.0、PyTorch 2.12.0、Python 3.12、Ubuntu 24.04、amd-aiter 0.1.21.post2）。缺失按原因分三类：ROCm 上不支持（CUDA 专属库、PTX、SM 门控核、CuTe DSL）、没有 ROCm 实现（普通核）、能导入但调用失败（norm 与量化 norm 算子）。

局限

  • 只针对 CDNA3/CDNA4 两个架构，支持矩阵由 arch_caps.py 一张表生成。
  • FP8 KV 缓存跨后端读写有静默读错的风险。
  • torch.compile 在 ROCm 上没有后端支持。
  • 部分上游模块缺失，且 layernorm 类算子能导入、调用时才失败，容易误判。

可复用的点

  • 逐调用、逐架构的路由表（arch_caps.py）是“同一 API、双后端”设计的可复用模式：路由规则先实测、再写表、支持矩阵由表生成。
  • wrapper.backend 与 wrapper.backend_fallback_reason 的可观测性设计：每次调用都报告选了哪个后端、为什么拒绝另一个。
  • CDNA4 的 ds_read_b64_tr_b16 转置读取指令：一条指令替换 6 次跨通道洗牌，种子重算、共享内存排布不变。
  • FP8 编码不对称的教训：KV 缓存的读写双方必须用同一编码，静默读错比报错更危险。
