MXFP8 进 TorchTitan：权重生命周期、[2,F,D] 叠放与梯度累积融合

  • 原文：Making MXFP8 Work in TorchTitan（PyTorch DevLog，Animesh Jain，2026-11-12）
  • 主题：低精度量化（MXFP8）、训练框架、并行策略（训练）
  • 星级：⭐⭐⭐⭐（重点阅读）
  • 一句话要点：MXFP8 的 kernel 不是难点，难点是让它与 FSDP、张量并行、流水线并行组合：权重生命周期搬进 FSDP、MoE 融合权重按 [2,F,D] 叠放、FSDP 梯度 dtype 契约改成 grad_dtype，三处改动让量化只做一次、TP 切分与 32x32 量化块不再打架、梯度累积直接融进 wgrad 的 matmul。

格式与配方

MXFP8 是 Blackwell 上原生的 FP8 格式：每 32 个连续值共享一个 scale，scale 用 e8m0（2 的幂）存。单个离群值只影响自己所在块的精度，不会逼整行或整列共用一个 scale。Hopper 也有快速 FP8 matmul，但块级缩放要在软件里模拟，为了省开销，Hopper 配方偏好 per-row / per-column 的粗 scale；Blackwell 的 Tensor Core 在 matmul 内部直接应用 scale，细粒度缩放才真正划算，MXFP8 正在成为训练的默认格式。

TorchTitan 的配方：权重用 32x32 块，前向激活用 1x32 块。激活不用 32x32 的原因是因果泄漏：一个激活矩阵每行是一个 token，32x32 的 tile 让 32 个 token 共享 scale，token 32 的离群值改了 scale，就会改变 token 1 的舍入、进而改变 token 1 的输出。前向里 X 沿行按 1x32 量化（沿输入特征约简），wgrad 里同一个 X 沿列按 32x1 量化；dY 同理。配方只覆盖带学习权重的大 matmul：DeepSeek-V3 里是注意力投影，以及共享专家与路由专家里的 gate、up、down 投影。

权重生命周期搬进 FSDP

旧实现的问题在生命周期。TorchTitan 原先的 MXFP8 支持靠 TorchAO 的 autograd.Function，它看不到 FSDP 的运行时（也不知道 reshard_after_forward 这类标志），结果是每个 microbatch 的前向和反向各量化一次权重，还要一直留着未分片的 bf16 参数副本——既多算，又多占显存。

改动是重划 TorchAO 与 TorchTitan 的边界：TorchAO 只提供 kernel，TorchTitan 掌握 autograd.Function，权重准备与生命周期管理搬进 FSDP 的生命周期——用一个实现 fsdp_post_all_gather 的 tensor subclass，让它完整看到 FSDP 运行时。流水线并行 + reshard_after_forward=False 时，权重在 all-gather 后只量化一次，bf16 副本随即释放，MXFP8 权重跨 microbatch 复用，这就是一台机器上能做的最少工作量。

没有 PP 的典型 FSDP 配置（reshard_after_forward=True）下，前向和反向各 unshard、量化一次，多算了另一套 scale；但量化 kernel 本来就要同时产出 MXFP8 数据和两套 scale，多产一套的成本很小，团队选择保持 hook 简单、两套都准备。仍不完美的一点：all-gather 仍然走 bf16——Wei Feng 的 FlexShard 正在解决这个问题。

[2,F,D] 叠放：量化块与 TP 切分兼得

融合 MoE 的 gate/up 权重（w1、w3，各 [F,D]）有三种摆法。拼接成 [2F,D]：量化没问题（边界对齐 32 行时每个 32x32 tile 都落在单个投影内），但沿融合维做连续二路 TP 切分后，rank 0 拿到全部 w1、rank 1 拿到全部 w3；SwiGLU 要求每 rank 拿到 gate 与 up 的对应切片才能在本地相乘。交错行：TP 切分没问题，但 32x32 tile 混了 w1 和 w3 的行，两个投影量程不同时，一个投影的离群值会给另一个投影定 scale、让它舍入更粗。

堆叠成 [2,F,D]、TP 沿第 1 维切分：每 rank 拿到 w1 与 w3 的对应切片，每个 32x32 量化块也完整落在 w1 或 w3 内部，两边都满足。这是全文最漂亮的一个结论：布局的选择同时决定了量化和并行能不能组合。

梯度累积融进 wgrad，FSDP 契约改 grad_dtype

每个 microbatch 产生一个权重梯度，PyTorch autograd 本来用单独的 AccumulateGrad 操作把它加进运行梯度；但 wgrad 本身就是一个 matmul，累加可以直接融进它的 epilogue、直接写进运行梯度。MXFP8 下 scaled_mm 变成 scaled_addmm_，BF16 下 mm 变成 addmm_。

挡路的是 FSDP 的旧契约：梯度必须与参数同 dtype。参数在计算时是 bf16，matmul 产出的梯度就是 bf16，FSDP 再把它上转成 fp32 做 reduce——多了一次无意义的往返。FSDP 与 TorchTitan 团队讨论后改了契约：FSDP 现在支持 grad_dtype，参数的梯度可以与参数不同 dtype；未分片梯度直接就是 fp32，往返消失，融合只剩写一个 autograd.Function 的事。DistMoE 的新开源 MoE kernel 同样支持 MXFP8，复用同一套 FSDP 生命周期保证。

为什么值得读

三处改动都是"接口边界"层面的工作，不是 kernel：量化生命周期归 FSDP 管、融合权重布局同时满足两种约束、梯度 dtype 契约放宽。做低精度训练集成的人最容易在这里踩坑——kernel 跑通只是开始，真正决定性能的是权重在分布式运行时里被量化几次、留几个副本、走几次 dtype 转换。
