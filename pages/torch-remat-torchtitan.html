torch_remat 进 TorchTitan：命名 region 做分布式激活重算

  • 原文：torch_remat in TorchTitan（PyTorch DevLog，2026-11-19）
  • 主题：训练框架、激活重算、并行策略（训练）
  • 星级：⭐⭐⭐⭐（重点阅读）
  • 一句话要点：TorchTitan 用 torch_remat 做激活检查点：模型源码里的命名 region 替代 aten 级别的 SAC policy；分布式重放要管集合通信、副作用与非确定性路由；缺 early stop 导致重算反而比存更占显存，包一层 always-saved region 就修好。

从 aten policy 到命名 region

激活检查点的想法很简单：前向丢掉一些张量，反向需要时再重算，用多算换显存。但分布式训练里"再跑一次前向"还意味着再跑一次集合通信、再更新一次计数器（副作用）、再做一次路由决策。

torch.utils.checkpoint 有两种做法：全量检查点（反向重算整个块，省显存但 matmul 这类重算很贵）、选择性检查点 SAC（重放块但保留选中操作的输出，跳过这些操作；policy_fn 按 aten op 名决定存还是重算，例如 matmul 计数偶数存、奇数重算）。SAC 用 TorchDispatchMode 拦截 aten 操作，有 CPU 开销，决策发生在 aten 层、离模型源码很远。

torch_remat 把选择表达在源码同一层：用 remat.region 包一个函数、给它一个有意义的名字（如 inner_attention），配置直接控制这个 region 的 save/recompute 策略。没有 TorchDispatchMode，所以快；在模型代码里直接写清哪些 region 存、哪些重算，是个很大的体验改进。credit 归 Edward Yang（torch_remat）与 Jeffrey Wan（早期的 torch.utils.checkpoint 基础）。

region 边界怎么划：重算成本除以释放的显存

边界放哪，取决于两个问题：重算这个操作要花多少时间、能释放多少被存的显存——大致就是"单位显存的重算成本"。便宜且占大张量的操作是重算的好候选，贵且省得少的是存的好候选。团队据此列了一张"永远重算"的操作表（如 residual_add），这些操作根本不建 region。

还有一笔"保存 region 的输出税"：一个 region 被标为 save、重放时跳过，它的输出 y 必须留着给后面的操作重放用——在全量检查点里，这个中间张量 y 可能根本不用存（没有任何反向公式需要它），但为了重放必须保活。torch_remat 用 recompute_needs_tensor 保住这类张量，而且它们计入峰值显存——这一点在 early stop 一节会反噬。

集合通信也要自己的 region

集合通信会改变张量的布局，存哪一侧显存代价不同。张量并行里有两个例子：ColumnParallelLinear 是 matmul 后跟 all-gather，RowParallelLinear 是 matmul 后跟 reduce-scatter。如果只存 matmul 输出、重算 reduce-scatter，大的 partial 输出就得一直留着；把 reduce-scatter 的输出也存下来，重放才能用更小的、已约简的分片。

问题是 TorchTitan 的集合通信原来由 reshard 逻辑隐式插入，根本没有地方包 region。团队先把它们显式化：ColumnParallelLinear 接管自己的输入 gather，RowParallelLinear 接管自己的输出 reduce-scatter，MoE 的 TP→EP 切换也显式化——这项工作后来长成一个独立项目，把隐式 reshard 逻辑从 Titan 里彻底移除（基于 Pian Pawakapan 的 SPMD types 基础）。

重放必须逐比特一致：计数器与路由

重放前向必须复现原前向（逐比特相等），集成时遇到两个违反。第一，计数器跑了两次：辅助 loss 的代码在前向数 token，重算时又数一次；旧的全量检查点路径靠藏在代码里的一次除以二掩盖，torch_remat 可以查 is_recomputing、重放时跳过计数更新，把这个 workaround 删掉。第二，路由必须一致：top_k 不是确定性的，重算路由选了不同的专家，反向就走了一条与原前向不同的计算图，极难调试——所以把路由做成固定的 recompute=False region，重放复用原始决策；周围的 region 用户可以调，这一个为正确性而锁定。

early stop 缺失：重算反而更占显存

torch.utils.checkpoint 有个 neat 的优化叫 early stop：重放时一旦生成了反向所需的全部张量就停下，后面的操作根本不跑。看 MoE 块的结尾：combine 之后，一个 add 合并共享专家与路由专家的输出，另一个 add 把结果加回残差流；combine 为反向存了张量，两个 add 什么都不存——对 a + b 来说反向只是把 dY 传给两个输入。重放可以在 combine 处停下、跳过两个 add，实测性能提升 24%。

torch_remat 不支持 early stop，所以丢了这个优化；更大的意外在显存：团队把 add 放在 region 外（因为便宜、永远重算），重放现在必须重跑它们，而要重跑就得用 recompute_needs_tensor 保活第一个 residual add 的输入——这些输入反向根本不需要，只为重放而存，还计入峰值显存。这是罕见的重算比存更占显存的情形。

修复很简单：把两个 add 包进 always-saved region。既不用再存第一个 residual add 的输入，也跳过了重放时的 add 计算。全部 region 设为 save 时，Qwen3 MoE 的激活显存从 8.18 降到 7.93 GiB，DeepSeek-V3 16B 从 9.11 降到 8.67 GiB（FSDP4 + EP4）。

结果：128 种 policy 的显存-时间 Pareto 前沿

有了这些 region，就可以探索不同的 save/recompute 组合、画出峰值显存对步时间的曲线。DeepSeek-V3 16B 上 128 种 remat policy 的 Pareto 前沿给出了一组可用的配置；SAC 也能做到，但命名 region 让选择更容易表达和检查。穷举在 region 很多时很贵，TorchTitan 的 ACTIVATION_REMAT.md 还描述了一种贪心方法，用更少的运行找到好配置。分布式训练里并行配置与重算选择都让显存呈离散台阶变化，这条曲线让人看清哪些配置装得进显存预算、为额外余量要付出多少性能。

为什么值得读

全文最有价值的是三处"分布式让简单想法变复杂"的实例：集合通信需要自己的 region（还得先把隐式通信显式化）、重放要逐比特一致（计数器与路由各钉死一处）、缺 early stop 时重算反而更占显存。做分布式训练框架的人，读完就知道 activation checkpointing 的坑不在 checkpointing 本身，在重放与原前向不一致的每一处细节。
