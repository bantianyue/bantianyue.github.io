教 27B 模型写 Triton 核：SFT 加 GPU Gym 强化学习

原文：GPU Kernels, Part 2: Teaching a 27B Model to Write Triton Kernels with SFT and a GPU Gym（g-factor，2026-11-03）

为什么值得读

这是一篇把"教模型写 GPU 核"从头做到尾的工程复盘：SFT 数据集里的 2,034 个核在 H100 上逐个重验，GRPO 式强化学习在 GPU gym 里练，每个答案都编译、校验、计时。最有价值的部分不是成绩，而是 7 版 gym 各坏一次的故障复盘，以及一个反直觉的结论——gym 奖励纯 Triton，考试奖励混合解，Level 2 的正确率因此一动不动。

核心结论

  • 两阶段训练把 Qwen3.8-27B 的 KernelBench 1–2 级正确率从 21.5% 推到 29.5%，正确且快过 eager PyTorch 的核从 7.0% 涨到 9.5%。Level 1 正确 31→47 道，快核 8→15 道。
  • 开中等思考再打一次分：正确率 29.5%→41.0%，Level 2 几乎翻倍（12→23 道）；但快过 eager 的核只从 19 个涨到 22 个。推理买正确率，不买速度。
  • 前沿模型在同一套题上领先 20 倍（Level 2 的 fast₁ 81 对 4），几乎全靠混合 cuDNN + Triton 解。

两阶段训练

基座 Qwen3.8-27B 开箱即懂基本的 Triton 语法，大约五分之四的答案能无语法错误地编译执行。缺的是数值精度与打败 PyTorch 需要的架构直觉。

第一阶段 SFT：2,034 个已验证问答对，全部在 H100 上按生产规模重验。来源是 siro1 收集的 Kimi K2 解 KernelBook 模块（每模块最多两个解），张量放大到约 100 万元素，token 集 Jaccard 相似度超 0.6 的问题一律清除，静态 AST 检查剔掉 forward() 里回落到 PyTorch 算子的解，再加 682 个早期 gym 探索跑出的成功解。其中 1,624 个在目标规模上跑赢 torch.compile。rank-8 LoRA adapter 训 2 个 epoch（3,674 步，学习率 2e-4），单张 H100 上大约 5 小时。

第二阶段 RL：gym 采用 OpenEnv 式架构，每集一个 worker 提供参考 PyTorch 模块，模型起草实现，隔离的 GPU 子进程在 H100 上做基准。GRPO 式每任务 8 个答案一组，CISPO 损失，REPO-R 熵控制，KL β=0.08，学习率 1e-5，300 步约 28 小时。

GPU gym：五道门与奖励

每份答案过五道验证门：静态策略沙箱（白名单 import）、编译与启动验证（经 CUDA 事件确认 Triton 核真的启动）、算力隔离（forward() 期间禁用 PyTorch 原生算力，混合任务只允许一次 cuBLAS/cuDNN 调用）、五个隐藏测试用例（标称、3 倍、0.01 倍、符号取反、绝对值，FP32 容差 1e-4）、低方差计时（方差低于 10% 才采纳）。

奖励函数平衡正确性与性能：1–3 号门是硬要求，失败直接归零；c 是通过的隐藏测试用例占比，v 是实测加速比，ρ 检查计时稳定性，e 惩罚工具折腾。速度奖励严格设门，五个隐藏用例全部干净通过且计时稳定才有速度分。速度占比按对数从 0.75 倍涨到 4 倍。

两种作答方式：单轮模式占 25%（照 KernelBench prompt 一次性作答），多轮修复模式占 75%（可调 submit_kernel、inspect_evaluation，最多迭代 4 次）。最终跑里模型解出 63.8% 的修复集，单轮 50.5%。

7 版 gym，每版各坏一次

版本 故障 修复
v3 复制参考辅助函数的答案被当不安全代码驳回 复制的辅助函数干净剥离，不再惩罚
v4 宽松 FP32 容差放过 KernelBench 后来驳回的核 输出必须在 1e-4 容差内匹配参考张量
v5 难算子族上一组 8 个样本经常全得零分，梯度为零 1e-2 宽松带内匹配给部分进度分
v6 速度奖励在 2 倍处截断饱和；小张量上编译开销让任何核都显得快 6–9 倍 张量放大到 1–3,200 万元素，改 0.75–4 倍对数速度奖励
v7 没有任何验证确认 Triton 核真的在 GPU 上跑了 引入原生执行门，经 CUDA 事件确认核启动
v8 gym 与 KernelBench 脱节；一个 PyTorch 内部 import 能绕过算力守卫；种子 bug 只抽了 966 行里的 69 行 新增 14 个算子族、单轮模式、严格 import 白名单、修复行哈希
v9 复杂算子族解出率仍接近零 引入分阶段课程练习（脚手架与尾声任务）

两个故障最能说明奖励 bug 有多微妙。指标饱和（v5）：每个通过的核都拿满分 1.0，梯度对进一步优化零压力。沙箱绕过（v8）：模型还没发现漏洞，但留一个可利用的洞就是定时炸弹。

分阶段练习解决了冷启动：之前零有效样本的算子族开始提供稳定的梯度反馈。

gym 与 KernelBench 的三处错位

多数基准收益来得早：SFT 期间与 RL 前 100 步。之后 KernelBench 进入平台期，gym 指标却继续爬。v9 四个季度 gym 解出率 73.4%→59.0%→54.9%→61.7%，KernelBench fast₁ 却是 9.5%、9.5%、8.5%、8.0%。

  1. 速度目标不一样：gym 拿 torch.compile 当速度基线，KernelBench 拿 eager PyTorch。在 gym 的大 FP32 张量尺寸下，编译后的 PyTorch 反而常常更慢。86.8% 的正确训练核打败 torch.compile，只有 61.4% 打败 eager PyTorch；26.2% 通过的核拿了正速度奖励，实际却比 eager 慢。编译后运行时的中位数比 eager 慢 2.1 倍。
  2. Level 2 的策略不一样：Level 2 是 63 个卷积与 36 个 GEMM 任务，各配一段逐元素尾巴。胜出的打法是混合实现：核心 GEMM 或卷积留在 cuBLAS/cuDNN，只给融合激活尾巴写 Triton 核。基座 Qwen 自然采用这个策略（55% 的时间），早期一个检查点产出 11 个快速混合解。但 SFT 筛选滤掉了混合代码，gym 封了 PyTorch 算力，SFT 后的模型只在 8% 的时间提交混合解。对比之下，Claude Opus 与 GPT-6 在 61% 到 93% 的 Level 2 答案里采用混合解。
  3. 练习不是考试：分阶段课程的收益集中在有辅助的变体上；面对无辅助的完整 Level 2 模块，模型难以合成完整的端到端核。

值得注意的点

  • SFT 数据集的去污染与纯 Triton 强制执行本意是质量门，却在 Level 2 上反噬：滤掉的混合解恰恰是胜出的策略。数据筛选的副作用要到基准上才看得见。
  • 奖励函数的基线选错比奖励形状更致命：对着 torch.compile 计时，等于教模型跨一道比真正考试更矮的栏。
  • 思考预算卡脖子：开思考后超过四分之一的答案撞上 8,192 token 预算。下一步要么用更大的预算评测，要么开着推理训 adapter。
  • 局限：单一训练种子与贪心采样；step 100 是 best-of-run 选择；前沿模型经厂商 CLI 单轮作答，条件不对称；全部评测在 FP32、KernelBench 1–2 级、H100 SXM 上进行。
  • 权重与数据集已开源：LoRA adapter 与已验证 SFT 数据集在 Hugging Face（g-factor-technologies）。
