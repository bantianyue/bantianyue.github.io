vLLM-GR：一次请求内跑完 beam 搜索

vLLM-GR：一次请求内跑完 beam 搜索，候选路径共享用户历史 KV（中文精读）

  • 原文：Announcing vLLM-GR: Efficient Inference for Generative Recommendation（https://vllm.ai/blog/2026-11-24-vllm-gr-announcement）
  • 收藏：2026-11-25
  • 主题：推理优化、并行策略（推理）、KV 缓存
  • 星级：⭐⭐⭐⭐（重点阅读）
  • 一句话要点：vLLM-GR 把生成式推荐的多路候选搜索做成 EngineCore 里的一次 beam session：候选路径共享缓存的用户历史 KV，每步在加速器上做 beam 选择并用父路径下标读后缀 KV，主机在设备执行当前阶段时准备下一阶段，形成 PDD 流水；beam 宽度 256 时 batch 4 与 8 的 P99 在 6 块加速器上都是所列后端里最低。

为什么值得读

生成式推荐把推荐问题改写成生成问题：根据观众历史，模型逐 token 生成候选物品的语义 ID（SID）。难点不在单条生成，而在一次请求要探索很多条候选路径、又要在延迟预算里返回。vLLM-GR 的解法是把整场搜索收进引擎：一次 beam session 管到底，候选路径共享同一份用户历史 KV，beam 选择与后缀 KV 读取都在加速器上完成，主机与设备用 PDD 流水重叠。机制、架构图、6 卡实测三部分都全，读完就能理解推荐推理与普通 LLM 服务在调度上的差别。

核心结论

  • beam session 是核心抽象：整个搜索由 EngineCore 里的一次会话管到底，记录候选路径怎么分叉；调度器把 prefill 与 decode 阶段发给 worker，每步模型 runner 给下一个 token 打分，beam 选择记录每条存活路径的分数与父路径，下一次解码用父路径下标读到正确的 KV 状态。
  • 候选路径共享用户历史 KV：跨 beam 共享 prompt KV，不用给每个候选复制一遍观众历史；第二次解码继承被选父路径的后缀 KV（suffix KV）。
  • PDD 流水重叠准备与执行：加速器执行当前阶段时，主机准备下一阶段。prefill 给第一个 SID 分量打分的同时主机准备 decode 1；decode 1 执行期间主机准备 decode 2。
  • 目录约束保证搜出来的 ID 能上架：搜索可限制在物品目录里的语义 ID，无效 SID 前缀直接丢掉（例子：A1 · B1 被过滤，因为没有物品以这个前缀开头）；全词表搜索跳过这层过滤。
  • 接口三选一：离线 Python 接口、OpenAI 兼容 HTTP、gRPC；一次响应返回候选序列与分数。每阶段 beam 宽度与每父路径候选上限可调，探索的 partial ID 比最终返回的更多。

架构：三色分工

  • 蓝色是复用的 vLLM 组件：HTTP 入口、模型前向等。
  • 黄色是 EngineCore 调度与 worker 执行的扩展。
  • 粉色是 vLLM-GR 新增部分：离线与 gRPC 入口、beam session、BeamAttn、后缀 KV，以及目录约束与全词表两种 beam 选择。

一次请求的例子：beam 宽度按 2 → 3 → 2 走，返回两个候选。目录过滤掉 A1 · B1，SID 与分数只是示例。

实测数字（P99 延迟）

基准在 4 块 NVIDIA GPU（H20、RTX PRO 6000、A100、L20）与 2 块昇腾 NPU（A2、A5）上跑 OneRec-1.7B（BF16），生成 3 个 token。两张总览图把输入长度固定在 1,024 token，比较 beam 宽度 256 与 128、batch 1、4、8。各图汇总的是计时定义、样本数与后端设置各不相同的独立基准运行；RTX PRO 6000 那次是 3 次预热后 48 个计时 batch 的整 batch P99，计时含把候选 ID 与分数返回主机、不含 HTTP；vLLM-GR 与 NVIDIA SID-GR 用候选池 K 等于 beam 宽度 W，SGLang Beam 用原生 2W 候选池。

规律：beam 宽度 256 时，batch 4 与 batch 8 下 vLLM-GR 的 P99 在 6 块加速器上都是所列后端里最低；batch 1 时 NVIDIA SID-GR 在个别卡上更快（RTX PRO 6000 上 28.25 ms 对 29.21 ms）。beam 宽度 128 时，最低延迟的后端随加速器与 batch 大小变化。L20 上部分曲线在最后一个配置前就断了，因为那些运行超出了设备内存；8,192 输入 token、batch 8 时，vLLM-GR 的 beam 宽度扫描跑到了 1,024。

路线图

  • 更广的模型支持：候选打分扩展到 HSTU、MTGR 与 RankMixer，给 OneTrans 加原生服务，探索总参数量更大的推荐模型（包括 MoE 模型）的服务优化。
  • 更灵活的 beam 搜索：价值感知的候选选择，给语义 ID 加更多输出头，更深的 SID 层级，可变长度生成（个别 beam 到 EOS 就停，释放槽位与 KV，接纳新请求）。
  • 在线组 batch 与调度：在线调度器决定什么时候组 batch、放哪些排队请求进组，让历史长度不同的请求一起跑，过载下保持队列有界；形状相近的 batch 分组，复用同一张捕获的计算图做重放，减少 padding。
  • 长历史与 KV 复用：优化 10,000 token 以上历史的 prefill，探索带线性或稀疏注意力的 beam 搜索；跨请求复用未变前缀的 KV 块。
  • 分布式推理与 KV 缓存：分布式 KV 缓存，让服务实例复用同一节点或另一节点上另一台设备的 KV 块。
  • 与上游 vLLM 更紧密集成：基于 vLLM 的引擎与平台接口，定期更新到更新的稳定版 vLLM。

值得注意的点

  • 版本：vLLM-GR 0.30.0 基于 vLLM 0.30.0，支持 NVIDIA GPU 与昇腾 NPU。
  • 基准口径不统一：各加速器图的计时定义、样本数、后端设置不同（L20 每配置 100 到 1,000 个计时 batch；昇腾上 vLLM-GR 与 xLLM 用目录约束表，SGLang 的约束设置没有记录在摘要里；RTX PRO 6000 之外的预热次数没有给出；确切后端版本没有给出），跨卡横向比较时以总览图为准，细节以各硬件小节为准。
  • 与 11 月 19 日的 SGLang Megakernel、11 月 24 日的 Miles 真 On-Policy 是同一条推理优化主线：把关键路径上的工作移出串行段、让一次 launch 或一次会话做更多事。
