-从零训练：冷启动EAGLE3.1草稿头，单台8卡MI350X节点跑通五段管线，目标模型为MXFP4量化的MoE模型MiniMax-M3。

-开箱工作流：Quark 0.13打包YAML配方与CLI，Qwen3-8B快速上手已GPU验证，大模型最佳配方覆盖MXFP4 MoE目标。

-实测数据：SPEED-Bench平均接受长度2.81，代码3.33最高；单卡输出吞吐415.2 tokens/s，延迟中位数9.68秒。

服务侧跑通之后，训练侧是另一半：Quark团队在单台8卡MI350X节点上，用ROCm、vLLM与TorchSpec组成的原生栈，从零为MXFP4量化的MoE目标模型MiniMax-M3训练EAGLE3.1草稿模型。

实测口径为官方SPEED-Bench：平均接受长度2.81，1K到32K上下文保持稳定；单卡输出吞吐415.2 tokens/s，比非推测基线高1.47倍，延迟中位数从13.15秒降到9.68秒。

草稿模型质量为何重要

标准自回归解码中，目标模型每步只产一个token。推测解码打破这个瓶颈：小草稿模型一次提议多个后续token，目标模型单次前向并行验证，接受的token成批输出，从首个拒绝处恢复。由于每个输出token都经过目标模型验证，推测解码无损：目标模型的输出分布保持不变。

接受长度（AL）衡量草稿是否在干活：每次目标模型验证步骤平均输出的token数。AL为1.0意味着草稿除保底token外没有加速；接受长度越高，目标模型每次验证确认的token越多，草稿值得认真训练。

EAGLE历代演进：EAGLE做特征层起草，EAGLE2提升接受率，EAGLE3把目标模型的低、中、高层特征与训练时测试目标结合。设计让草稿与验证器紧密对齐。EAGLE3草稿不是挂在旁边的通用小语言模型，而是针对目标模型内部表示训练，提议更容易被验证器接受。

EAGLE3与EAGLE3.1之别：本工作训练的是EAGLE3.1草稿。EAGLE3.1不是新方法，而是EAGLE3的小幅向后兼容改进：保留相同的特征层起草设计与相同的vLLM服务格式（LlamaForCausalLMEagle3），在草稿头内增加归一化以稳定训练。这对从零训练很关键。下文EAGLE3指方法与技术栈统称，EAGLE3.1指实际训练的草稿变体。

EAGLE3.1训练管线

概括来看，EAGLE3.1草稿训练走五段管线。训练时目标模型提供监督草稿的隐藏状态；服务时验证草稿提议的token。

  • 在策略数据：目标模型为覆盖多领域的提示池重新生成回答。用目标模型自身输出而非现成参考答案训练，让草稿对齐服务时真正需要预测的分布。
  • 隐藏状态抽取：实时vLLM-ROCm引擎运行目标模型，把多层隐藏状态流式送给训练器，提供EAGLE3所需的低、中、高层特征。
  • 冷启动EAGLE3.1训练：草稿头从随机初始化出发，以训练时测试（TTT）目标训练，用FSDP2跨GPU分片。
  • 导出：训练好的草稿转为vLLM可加载的LlamaForCausalLMEagle3检查点，可直接放入推测解码服务器。
  • 服务与评估：导出的草稿用vLLM部署，SPEED-Bench度量接受长度。

完整循环跑在单台8卡MI350X节点上：部分GPU承载产出隐藏状态的vLLM目标引擎，其余GPU跑FSDP2草稿训练器。

YAML与CLI工作流

Quark 0.13把EAGLE3训练打包成可复用YAML配方与小型CLI。ROCm环境准备一次，再按目标选工作流：

  • Qwen3-8B快速上手是经过完整GPU验证、可复现的路径。
  • EAGLE-3大模型最佳配方以MiniMax-M3-MXFP4为例，演示如何把工作流适配到大型量化模型。

Qwen3-8B快速上手

Qwen3-8B是Quark 0.13验证过的工作流：CLI生成在策略数据、在8块GPU上训练、导出vLLM兼容草稿，并对基线与推测服务做基准测试。用--base_model选目标模型。

环境准备一次：setup命令幂等，检查Docker与ROCm GPU访问，准备验证过的训练与服务依赖及ROCm镜像，下载Qwen3-8B，并记录环境清单以便复现。

python3 -m quark.experimental.speculative_decoding.setup --base_model Qwen/Qwen3-8B

运行验证过的默认配方：最短端到端形式。打包的recipes/eagle3_default.yaml提供数据、训练、导出与基准默认值，用户只需指明目标模型。

python3 -m quark.experimental.speculative_decoding.run --base_model Qwen/Qwen3-8B

需要显式配方形式时：用--base_model设定目标。

python3 -m quark.experimental.speculative_decoding.run \
     --config recipes/eagle3_default.yaml \
     --base_model Qwen/Qwen3-8B \
     training.output_dir=ckpts/qwen3-8b-eagle3 training.num_epochs=2

大模型最佳配方:MiniMax-M3示例

最佳配方是可移植基线，而非针对某个LLM调好的配置。完整运行时，先从domain_manifest.full.example.yaml创建清单，把占位符换成评审过的数据源与许可信息，调整领域上限与留出策略，并使用全新的输出目录。选定的目标在策略上重新生成回答，运行时长与实测结果取决于清单与服务配置。

python3 -m quark.experimental.speculative_decoding.setup \
    --base_model amd/MiniMax-M3-MXFP4

python3 -m quark.experimental.speculative_decoding.run \
    --config recipes/eagle3_mxfp4_moe.yaml \
    --base_model amd/MiniMax-M3-MXFP4 \
    execution.profile=full \
    data.domain_manifest=/absolute/path/to/domain_manifest.yaml \
    training.output_dir=ckpts/minimax-m3-eagle3-full

打包默认配方

多数用户无需编辑YAML。核心用户侧字段如下；打包文件还保留更底层的草稿架构与原生参考设置。默认值选定验证过的8卡完整管线，同时把底层实现细节挡在用户工作流之外。

按默认值跑完，vLLM可加载的草稿与report.json落在training.output_dir下。可复用的模型与在策略数据资产会被缓存，后续配方运行更快，同时保留复现结果所需的精确配置与环境。

ROCm训练栈支撑

在ROCm上原生跑通管线，需要几块拼图协同，让训练、抽取与服务留在同一套AMD技术栈上：

  • vLLM-ROCm隐藏状态抽取：EAGLE3训练需要目标模型的中间隐藏状态，不只是输出token。所用的vLLM-ROCm构建在worker中暴露隐藏状态抽取路径，让标准vLLM服务进程在AMD GPU上充当训练的特征源。
  • MXFP4 MoE目标加载：目标amd/MiniMax-M3-MXFP4是大型MXFP4量化MoE模型。在vLLM on ROCm下用AITER MoE快速路径与合适的注意力后端正确加载运行后，生产用的同一量化模型也能在训练中担任验证器与隐藏状态源。
  • TorchSpec流式训练器：TorchSpec的解耦EAGLE3训练器把多个vLLM抽取引擎与FSDP2训练秩配对，在二者之间流式传输隐藏状态。大型MoE目标无需把数TB特征写盘，就能在单节点上监督草稿。

拼在一起，训练到服务的循环成为单一ROCm原生工作流：Quark负责量化目标，ROCm与vLLM负责抽取与服务，TorchSpec负责训练核心。

训练策略

以下选择比任何固定配方对草稿质量影响更大：

  • 冷启动，从零开始：草稿头从随机初始化出发，绝不用已有草稿热启动，保证结果干净、独立训练。
  • 在策略数据是最重要的因素：最关键的选择是在目标模型自身输出分布上取数据。目标模型跨广泛领域组合重新生成回答：通用对话与指令遵循、多语言内容，以及相当比例的代码与数学。草稿由此学会预测目标模型实际产出的内容。
  • 训练时测试（TTT）目标：训练中不只预测紧邻的下一个token，而是把草稿展开多步。这教会草稿连续提议多个token，与推理时的用法一致。
  • 对话模板保真：训练数据使用目标模型精确的对话模板。训练模板一旦偏离服务模板，接受长度会悄悄下降；保持二者完全一致才能保住草稿质量。
  • EAGLE3.1归一化：EAGLE3.1草稿头新增的归一化让冷启动训练更稳定，对从零训练的大型草稿尤其重要。

接受长度由什么决定

这次运行的两点观察，可推广到AMD Instinct上的EAGLE3草稿训练：

  • 领域覆盖直接体现在分领域接受长度上：代码与数学这类结构化、高信号领域接受长度最高；角色扮演与创意写作这类开放式、高熵领域本质上更难预测，落在低位，这一规律与草稿无关。
  • 接受长度在长上下文保持稳定：草稿的接受长度从1K到32K token基本持平，草稿质量不随上下文增长而下滑。
