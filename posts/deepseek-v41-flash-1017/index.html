结论先行:主模型只动了1%,草稿模型几乎重训

DeepSeek把V4.1-Flash-1017称为"小版本更新"，config.json字节级一致，96085个tensor的名字、dtype、shape全对上，48个safetensors分片每一个的SHA-256都变了。warmctl用HTTP range read拉了2421个tensor做差分：主模型整体只动了约1%，而推测解码用的草稿模型（MTP + DSpark）几乎是重新训练的。

模型卡上的数字：Terminal-Bench 4.0 +11分，ProgramBench +9分，无工具HLE +5.8。输出更短、任务执行更快。小版本号通常意味着轻量微调，差分结果说：推理、代码、agent任务的提升，主要来自草稿模型的重训，不是主模型的精修。

475GB的权重长什么样:先看文件结构

两个仓库结构完全一致。96,085个tensor铺在48个分片上，config字节相同。475GB的分布决定了微调能动哪、不能动哪：

40层里每层384个路由专家是FP4（每字节pack 2个code，每32个一块配一个E8M0 scale），占checkpoint的57%。两个Engram层是查找表，每表3.84亿行FP8，当内存读，占40%。注意力投影和共享专家是FP8。

48个分片SHA全变，说明没有哪个分片被原样保留。但"都变了"不等于"都重要"，要看每个tensor变了多少。

方法:不下载950GB,怎么做差分

safetensors文件头是一段JSON，给出每个tensor的类型、shape和字节范围。先range read每个分片头部的几KB，就把整个checkpoint的tensor地图画出来。然后对每个tensor，在25% 和75% 位置各读一个16KB窗口，两个版本对比。

每个tensor算两个数：Codes changed（bit不一样的存储值占比），Relative change（解码后 ‖Δ‖ / ‖W‖）。BF16/F32 tensor的relative change就是权重变化本身；FP4/FP8则在block scale之前的code上量。

采样策略：路由专家480个tensor，MTP路由专家36个，注意力投影200个，共享专家120个，MTP注意力+共享专家24个，Engram表2个，专家block scale 480个。

结果:1% 的主模型,98% 的草稿专家

主模型是典型的后训练签名：layer norm动0.8%，hyper-connection mixer动1.5%，token embedding动1.8%，输出头动1.5%，expert router动5.0%，sparse-attention indexer动5.8%。每个权重都动了，都没大动。

视觉部分动得更多：encoder动2.6%，把图像特征投影进语言模型的aligner动8.7%，和模型卡上的视觉benchmark提升对得上。

草稿栈是重训的。V4.1-Flash用3层MTP + DSpark head做推测解码，给主模型提候选token。全精度权重中位数动了9.4%，DSpark head动了37.3%。

上机:同样的引擎,换上新权重

架构没变，vLLM配置直接沿用：4×B200的1017 profile，张量并行 + 专家并行，单卡32GB FP8 KV cache，DSpark配5个draft token和192的推测窗口。

冷启动1196秒才出第一个token；warmctl up从page cache恢复热引擎只要78.4秒。CRIU是最大头（47.8秒），因为dump里带着引擎pinned在host内存的Engram表：326GB进程镜像对293GB权重。

复现:两个版本并排跑

1017是warmctl catalog里的独立条目，warmctl up deepseek-v41-flash-1017拉起新版的同时老版继续服务，直接对比。

差分脚本只有两个（headers.py和diff.py），纯标准库 + HTTP range request，换一对Hugging Face上的safetensors checkpoint就能用。

结论

"小版本更新"的标签下藏着不对称的改动：主模型1% 的轻触是后训练的常规操作，MTP/DSpark草稿栈98.5% 的解码值变化才是benchmark涨分的主因。推测解码的草稿质量直接决定端到端速度，DeepSeek把优化预算花在了刀刃上。

方法论上也有价值：safetensors的JSON头 + HTTP range read让950GB的差分不需要下载，两个短脚本就能复现。下次看到"minor update"，先diff再信。
